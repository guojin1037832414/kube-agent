## 一、问题1：Agent 权限应该设计几道防线？

### 1.1 建议架构（Depth of Defense）

| 防线层级 | 位置 | 职责 | 作用域 |
|---------|------|------|--------|
| L1 意图层过滤 | IntentRouter / Agent | 按用户角色过滤可用意图 | Experience |
| L2 Tool 注册中心预检 | ToolRegistry | 按 `@ToolPermission` 过滤 LLM 可见 Tool | 核心防御 |
| L3 Agent 入口二次校验 | AtlasAgentBase | 拦截 LLM 绕过或越权猜测 | 冗余防御 |
| L4 后端 API 鉴权 | kube-manager | `@Isolation` 最终兜底 | 最终防线 |

### 1.2 专业判断

**“不只一道后端兜底”，至少保留 L2 + L4。** 原因：
1. LLM 是天然不可信任的执行体，它不具备权限语义理解能力。ToolRegistry 预检（L2）等于帮 LLM 建立了语义沙盒——管理员工具压根不会出现在 system prompt 中，LLM 不会误引导用户。
2. Agent 层的执行校验（L3）用于应对 prompt injection 或 LLM 恶意构造的工具参数名。
3. 后端 API（L4）是**法律上**的最终安全保证，但不应作为**唯一**防线——如果 LLM 反复调用无权限 API，用户体验极差，也会浪费 Token。

## 二、问题2：ThreadLocal 在 CompletableFuture 异步链下的安全问题

### 2.1 当前代码风险点

```java
// AtlasOrchestrator.java L81-82
CompletableFuture.runAsync(() -> {
    // ... 运行在新线程（ForkJoinPool.commonPool 或自定义线程池）
    intentRouter.route(...);
    agent.executeIntent(...);      // → 内部调用 toolRegistry.isVisible()
    tool.execute(...);             // → 如需要用户 token，此处丢失
});
```

- `AuthTokenFilter` 在主线程（Tomcat NIO 线程）绑定 Token 到 `ThreadLocal`。
- `CompletableFuture.runAsync()` 提交到线程池后：**线程切换 → ThreadLocal 完全丢失**。
- `UserPermissionContext.current()` 在异步线程中永远返回 `Optional.empty()`。
- **现实影响**：如果当前线程公平轮转，普通用户的请求可能恰好命中之前管理员请求的线程并残留旧 Token；更常见的是 Token 为空导致所有 `ADMIN_ONLY` / `AUTHENTICATED` 工具被误拦截。

### 2.2 修复方案（优先级排序）

#### 方案A（推荐）：显式上下文传递（最小侵入）

将 `UserPermission` 作为参数/Callable 闭包显式透传，放弃 ThreadLocal 依赖：

```java
// AtlasOrchestrator
@Override
public SseEmitter streamChat(@RequestBody ChatRequest request) {
    // 1. 在主线程解析权限（此时 ThreadLocal 有效）
    UserPermissionContext.UserPermission user = userPermissionContext.current().orElse(null);
    
    CompletableFuture.runAsync(() -> {
        // 2. 显式设置到当前线程（线程池线程）
        if (user != null) userPermissionContext.bind(user.token());
        try {
            // ... execute
        } finally {
            userPermissionContext.unbind(); // 必须清理
        }
    });
}
```

#### 方案B（最佳实践）：自定义 TaskDecorator（Spring 推荐）

```java
@Configuration
public class AsyncConfig {
    @Bean(name = "atlasExecutor")
    public Executor atlasExecutor(UserPermissionContext ctx) {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setTaskDecorator(runnable -> {
            var user = ctx.current().orElse(null);
            return () -> {
                if (user != null) ctx.bind(user.token());
                try { runnable.run(); }
                finally { ctx.unbind(); }
            };
        });
        // ... other config
        return executor;
    }
}

// 使用时指定
CompletableFuture.runAsync(() -> { ... }, atlasExecutor);
```

#### 方案C（高安全场景）：使用阿里的 TransmittableThreadLocal

适用于更复杂的线程池模型。

### 2.3 额外发现：KubeManagerHttpClient 未透传用户 Token

```java
// KubeManagerHttpClient.java
.header("Authorization", "Bearer " + authToken)  // ← 用的是系统账号(sysadmin)硬编码 Token
```

**安全风险：** 所有用户请求到后端都以 `sysadmin` 身份执行 → 后端 `@Isolation(SYS_ADMIN_ONLY)` 形同虚设。

**修复：** `KubeManagerHttpClient` 应获取当前用户的真实 Token（从透传的上下文中取），而不是用服务账号：

```java
// 修改后（概念）
String userToken = Optional.ofNullable(userPermissionContext.current())
    .map(UserPermission::token)
    .orElseThrow(() -> new PermissionDeniedException("未认证"));
.header("Authorization", "Bearer " + userToken)
```

## 三、问题3：管理员专属操作 —— 静默过滤 vs 显性拒绝？

### 3.1 建议策略：两者结合，分场景

| 场景 | 推荐策略 | 理由 |
|------|---------|------|
| LLM 视野（system prompt / listByAgent） | **静默过滤** | LLM 不知道这些工具存在，不会误引导用户 |
| Agent 执行入口（executeTool / executeIntent） | **显性拒绝** | 如果 LLM 通过 prompt injection 猜测到工具名，给出明确越权提示 |
| 意图路由（canExecuteIntent） | **显性拒绝** | 告知用户“该操作需要管理员权限”，比“找不到”更友好 |

### 3.2 落地

- `ToolRegistry.listByAgent()` 保持 `isVisibleTo()` 过滤 → 静默。
- `ToolRegistry.resolve()` 越权抛 `PermissionDeniedException` → 显式。
- `AtlasAgentBase.gracefulDeny()` 返回结构化错误 → 显式。

## 四、问题4：后端 @Isolation 已存在，Agent 层是否还需预检？

### 4.1 结论

**必须保留 Agent 层预检（L2 + L3），且后端 Token 透出修复后 L4 才真正生效。**

### 4.2 原因

1. **职责分离**：Agent 层权限是“业务可见性”，后端 `@Isolation` 是“数据访问控制”。比对：后端 `/api/user/create` 允许 `ops_admin` 创建普通用户，但 Agent `user_create` 仅面向 `sys_admin`（因为 Agent 是 LLM 自然语言接口，权限应更保守）。
2. **性能**：LLM 反复调用越权 API 会导致延迟 + Token 浪费 + 日志噪音。
3. **当前后端已被绕过**：由于 `KubeManagerHttpClient` 使用系统账号，后端鉴权无效。

## 六、ToolRegistry 已知 Bug

### 6.1 重复检测逻辑在 put 之后

```java
// 当前代码（ATLAS/tool/core/ToolRegistry.java L78-82）
toolByName.put(name, tool);  // ← 先 put
if (toolByName.containsKey(name) && toolByName.get(name) != tool) {
    // ← 永远为 false，因为 put 后 get(name) == tool
    log.error("Tool名称冲突: '{}' 被多个类注册", name);
}
```

**修复方式：**

```java
BaseTool existing = toolByName.put(name, tool);
if (existing != null && existing != tool) {
    log.error("Tool名称冲突: '{}' 被多个类注册 (existing={}, new={})",
        name, existing.getClass().getName(), tool.getClass().getName());
}
```

或者先检测后 put：

```java
if (toolByName.containsKey(name)) {
    log.error("Tool名称冲突: '{}' 已被 {} 注册，忽略 {}",
        name, toolByName.get(name).getClass().getName(), tool.getClass().getName());
    continue;
}
toolByName.put(name, tool);
```
