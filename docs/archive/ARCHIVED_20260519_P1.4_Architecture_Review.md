## 1. ToolRegistry 的 bug 修复

### 1.1 当前代码分析

```java
@PostConstruct
public void init() {
    for (BaseTool tool : tools) {
        // ... 提取 name ...
        if (toolByName.containsKey(name)) {
            BaseTool existing = toolByName.get(name);
            if (existing != tool) {
                log.error("Tool名称冲突...");
            }
            continue;
        }
        toolByName.put(name, tool);   // 先检测再 put，逻辑正确
    }
}
```

**结论：当前 `init()` 的方法是 "先检测再 put"，重复检测逻辑本身是正确的。** 问题描述中提到的 "put 后永远不会触发" 在当前代码中已经修复。

### 1.2 但仍存在两个隐患

#### 隐患 A：Spring bean 初始化时序导致重复扫描同一 Tool

Spring 的 `@Component` + `@Autowired List<BaseTool>` 在某些场景中（如存在 `@Primary` 代理 bean）可能导致同一个物理类被注入两次：
- 原始实例 `NodeQueryTool@1a2b3c`
- CGLIB 代理 `NodeQueryTool$$Enhancer@4d5e6f`

当前代码 `if (existing != tool)` 用 `==` 比较引用，代理 bean 与原始 bean 不相等，会触发冲突日志，但不会抛出异常阻止启动。

**推荐方案：启动时遇到重复应强失败**

```java
if (toolByName.containsKey(name)) {
    BaseTool existing = toolByName.get(name);
    if (existing.getClass() == tool.getClass() ||
        existing.getClass().isAssignableFrom(tool.getClass()) ||
        tool.getClass().isAssignableFrom(existing.getClass())) {
        // 同一类被扫描两次（代理问题），取第一个，打 warn
        log.warn("Tool '{}' 被重复扫描（可能是CGLIB代理），忽略后续实例: {} vs {}",
            name, existing.getClass().getName(), tool.getClass().getName());
        continue;
    } else {
        // 真正的名称冲突，必须强失败
        throw new IllegalStateException(
            "Tool名称冲突: '" + name + "' 被两个不同类注册: "
            + existing.getClass().getName() + " vs " + tool.getClass().getName()
            + "。请检查 @AtlasToolMapping(name=...) 是否有重复。"
        );
    }
}
```

#### 隐患 B：ConcurrentHashMap 并发场景（多线程初始化）

当前用 `LinkedHashMap`，是单线程的。如果未来改为懒加载（多线程并发调用 `register()`），则需要：

```java
private final ConcurrentHashMap<String, BaseTool> toolByName = new ConcurrentHashMap<>();
BaseTool existing = toolByName.putIfAbsent(name, tool);
if (existing != null) {
    // 重复检测逻辑
}
```

> 当前推荐：保持 `@PostConstruct` 单线程初始化 + `LinkedHashMap`，无需改为 `ConcurrentHashMap`。

## 2. 权限检查的分放策略

### 2.1 核心矛盾

Spring AI Function Calling 的调用链路：
```
LLM -> ChatClient -> FunctionCallbackResolver -> MethodToolCallback -> BaseTool#execute()
```

**注意：这不是 Spring MVC 调用链，没有 DispatcherServlet、没有 HandlerInterceptor、没有 @PreAuthorize 的 AOP 拦截点。**

### 2.2 权限检查的「三道防线」模型

```
防线1：System Prompt 过滤（源头治理）
  - AtlasOrchestrator 调用 toolRegistry.buildSystemPrompt()
  - LLM "看不到" 越权 Tool
  -> 必须做，且是第一道防线

防线2：意图路由层过滤（AtlasOrchestrator）
  - intentRouter.route() 之后，agent.execute() 之前
  - toolRegistry.canExecuteIntent(intentId) 二次校验
  -> 兜底：防止 LLM 幻觉或绕过系统提示

防线3：Tool 执行层过滤（可选，细粒度）
  - 在 BaseTool#execute() 入口处加 AOP/模板方法
  -> 用于：方法级更细粒度的权限（如 "只能删除自己的实例"）
```

### 2.3 @ToolPermission 挂载位置的推荐策略

#### 方案 A：类级别（当前做法）— 推荐，保持

```java
@Component
@AtlasToolMapping(name = "user_delete", ...)
@ToolPermission(ToolPermission.Policy.ADMIN_ONLY)
public class UserDeleteTool extends BaseTool { ... }
```

优点：
- 一个 Tool 对应一个意图，权限策略与意图天然一对一
- ToolRegistry 在 @PostConstruct 即完成索引，零运行时开销
- Spring AI 注册时即可过滤

#### 方案 B：方法级别 + @PreAuthorize — 不推荐在 Tool 层使用

```java
// 不推荐在 Spring AI Function Calling 链路中使用
@PreAuthorize("hasRole('admin')")
protected AtlasToolResult doExecute(Map<String, Object> params) { ... }
```

问题：
- Spring AI 的 MethodToolCallback 通过反射直接调用 execute()，不经过 Spring Security 的 SecurityContextHolder 初始化
- @PreAuthorize 依赖 MethodSecurityInterceptor，需要 Spring Security 的方法级安全开启 + SecurityContext 中的 Authentication
- 当前项目的 UserPermissionContext 是用自定义 ThreadLocal 实现的，与 Spring Security 的 SecurityContextHolder 不互通
- 强行接入需要额外注入 SecurityContext，增加复杂度，收益不大

### 2.4 最终推荐

| 防线 | 位置 | 机制 | 必要性 |
|---|---|---|---|
| 第一道 | ToolRegistry.buildSystemPromptForCurrentUser() | 类级 @ToolPermission | **必须** |
| 第二道 | AtlasOrchestrator.streamChat() 中 canExecuteIntent() | 类级 @ToolPermission | **必须** |
| 第三道 | BaseTool#execute() 中的 checkPermission() | 类级 @ToolPermission | 可选（当前不必） |
| 方法级 @PreAuthorize | doExecute() | Spring Security AOP | 不推荐（与 Spring AI 调用链不兼容） |

## 3. 测试策略

### 3.1 MockMvc vs 实际容器启动

| 维度 | MockMvc | 实际容器 (@SpringBootTest webEnvironment=RANDOM_PORT) |
|---|---|---|
| 启动速度 | 快（不启动 Tomcat） | 慢（3-10s） |
| HTTP 栈真实性 | 只到 DispatcherServlet | 完整 Tomcat |
| SSE 测试 | 难以测试流式响应 | 可用 WebTestClient |
| 权限上下文注入 | 需手动 Mock Filter | 真实 Filter 链路 |

推荐策略：分层测试
- 单元测试（JUnit + Mockito）：ToolRegistry.isVisible()、AsyncContextHolder.wrap()
- 集成测试 I（不启动 web）：ToolRegistry + UserPermissionContext Bean 交互
- 集成测试 II（RANDOM_PORT）：AtlasOrchestrator SSE 端到端、Token 透传全链路
- 集成测试 III（MockMvc）：仅验证 HTTP endpoint Filter（如权限检查在 Controller 层）

### 3.2 如何 mock 不同权限的用户

当前测试中的做法：
```java
String token = "token-regular-user";
userPermissionContext.onLogin(token, "zhangsan", "user", Set.of());
userPermissionContext.bind(token);
```

建议封装为 TestFixture：

```java
@TestComponent
public class PermissionTestFixture {
    @Autowired private UserPermissionContext userPermissionContext;

    public void asAnonymous() { userPermissionContext.unbind(); }

    public String asRegularUser(String username) {
        String token = "token-regular-" + username;
        userPermissionContext.onLogin(token, username, "user", Set.of());
        userPermissionContext.bind(token);
        return token;
    }

    public String asAdmin(String username) {
        String token = "token-admin-" + username;
        userPermissionContext.onLogin(token, username, "sys_admin", Set.of());
        userPermissionContext.bind(token);
        return token;
    }

    public void logout() {
        String token = userPermissionContext.getCurrentToken();
        if (token != null) userPermissionContext.onLogout(token);
        userPermissionContext.unbind();
    }
}
```

SSE 端到端权限测试示例：

## 4. KubeManagerHttpClient 的形态设计

### 4.1 当前实现分析

resolveToken() 流程：ThreadLocal 用户 Token -> 降级 sysadmin 统一登录。当前是 "用户 Token 优先 + 自动降级" 模式。

### 4.2 两种设计模式对比

#### 模式 A：application.yml 开关（粗粒度切换）

```yaml
atlas:
  backend:
    auth-mode: USER_TOKEN  # USER_TOKEN | SERVICE_ACCOUNT
```

优点：配置简单，一键切换，适合环境级切换
缺点：全局一刀切，无法混合使用

#### 模式 B：调用时传入 token 参数（细粒度控制）— 推荐

```java
public class KubeManagerHttpClient {
    // 面向 Tool：自动从 ThreadLocal 读取
    public Map<String, Object> get(String path, Map<String, Object> params) {
        return get(path, params, null);
    }

    // 面向 Admin/内部任务：显式传入 Token
    public Map<String, Object> get(String path, Map<String, Object> params, String explicitToken) {
        String token = (explicitToken != null) ? explicitToken : resolveToken();
        return executeGet(path, params, token);
    }
}
```

优点：Tool 层不需要关心 Token，Admin 后台任务可显式传入 service account token
缺点：API 多出 overload，但 Tool 代码无需修改

### 4.3 推荐方案：模式 B + 配置化降级策略（混合模式）

```java
@Component
public class KubeManagerHttpClient {

    public enum TokenStrategy {
        USER_TOKEN_FIRST,    // 优先用户Token，无则降级sysadmin（当前行为）
        USER_TOKEN_STRICT,   // 必须有用户Token，无则抛异常
        SERVICE_ACCOUNT      // 强制使用sysadmin统一账号
    }

    @Value("${atlas.backend.token-strategy:USER_TOKEN_FIRST}")
    private TokenStrategy tokenStrategy;

    // 无参便捷方法（Tool 用）
    public Map<String, Object> get(String path, Map<String, Object> params) {
        return get(path, params, null);
    }

    // 显式 Token 重载
    public Map<String, Object> get(String path, Map<String, Object> params, String explicitToken) {
        String token = resolveToken(explicitToken);
        return executeGet(path, params, token);
    }

    private String resolveToken(String explicitToken) {
        if (explicitToken != null && !explicitToken.isBlank()) {
            return explicitToken;  // 显式传入优先
        }
        switch (tokenStrategy) {
            case USER_TOKEN_STRICT:
                String strictToken = userPermissionContext.getCurrentToken();
                if (strictToken == null || strictToken.isBlank()) {
                    throw new IllegalStateException("USER_TOKEN_STRICT 模式要求请求必须携带 Token");
                }
                return strictToken;
            case USER_TOKEN_FIRST:
                String userToken = userPermissionContext.getCurrentToken();
                if (userToken != null && !userToken.isBlank()) return userToken;
                log.warn("ThreadLocal 无用户 Token，降级使用 sysadmin");
                return getFallbackToken();
            case SERVICE_ACCOUNT:
                return getFallbackToken();
            default:
                throw new IllegalStateException("Unknown strategy: " + tokenStrategy);
        }
    }
}
```

配置示例：
```yaml
# 开发/测试环境：宽松模式
atlas:
  backend:
    token-strategy: USER_TOKEN_FIRST

# 生产环境：严格模式
atlas:
  backend:
    token-strategy: USER_TOKEN_STRICT
```

后台任务显式使用：
```java
@Scheduled(fixedRate = 60000)
public void cleanupExpiredResources() {
    String sysadminToken = authService.loginAsSysadmin();
    client.post("/api/admin/cleanup", Map.of(), sysadminToken);
}
```
